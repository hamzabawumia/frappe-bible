# Frappe Framework: Choosing Your Implementation Approach

## 1. Introduction

In the first article, we mapped Frappe's three application environments — Desk, Portal, and API — and separated that decision from the choice of frontend technology (native UI, HTMX, Vue, React, and so on). That gave us a way to answer the question: **where does this feature live, and how is its interface built?**

This article zooms in one level further. Once you know where a feature lives, Frappe usually still hands you *several different plumbing paths* to actually build it — and picking between them is a real architectural decision, not a stylistic one.

We'll call this choice the **implementation approach**: the specific path chosen, from among several available, to realize a given capability that Frappe's framework already exposes. It's a narrower and more concrete idea than "architecture" — you're not deciding whether to use Desk or Portal, you're deciding, say, whether a customization should live as a file in your git repo wired through a hook, or as a database record editable from the UI.


The goal of this article is to name the recurring axes along which these choices repeat themselves, so that the next time you hit one of these forks, you recognize it instead of re-deriving it from scratch.

---

## 2. Extension Mechanism vs. Implementation Approach

It's worth being precise about two terms that are easy to conflate.

An **extension mechanism** is the general capability Frappe exposes — the fact that you *can* attach custom client-side behavior to a DocType, or add a field to it, or hook into its save event. This is the category.

An **implementation approach** is the specific path you take to realize that capability. The same extension mechanism ("attach JS to a DocType's form") can be implemented as:

- a `.js` file wired through the `doctype_js` hook in `hooks.py`, or
- a **Client Script** record stored in the database and edited through the Desk UI.

Both reach the same functional outcome. They differ in *where the customization lives and how it's delivered* — which turns out to be the single most recurring axis in Frappe development.

```text
Extension Mechanism
   "You can attach behavior to a DocType"
            │
            ├── Implementation Approach A: file + hook
            └── Implementation Approach B: DB record (UI-editable)
```

---

## 3. The Core Tension: File-Based vs. Record-Based

This tension isn't unique to client scripts. It resurfaces, almost identically, across a whole set of unrelated-looking Frappe subsystems:

| Concern | File-based (repo, git) | Record-based (DB, UI-editable) |
|---|---|---|
| Client-side scripting | `doctype_js` hook + `.js` file | **Client Script** doctype |
| Server-side event logic | `doc_events` in `hooks.py` | **Server Script** doctype |
| Field customization | DocType JSON (only if you own the doctype) | **Custom Field** + **Property Setter** |
| Print formats | Jinja template file in your app | **Print Format Builder** (stored in DB) |
| Reports | Script Report `.py` file | **Query Report** (SQL stored in DB) |
| Scheduled jobs | `scheduler_events` in `hooks.py` | — (no DB-record equivalent; always file-based) |

Every row is the same fork wearing a different costume: do you want this to be **code**, versioned in git, reviewed in pull requests, deployed deliberately — or do you want it to be **data**, editable by an admin at 2am without a deployment pipeline?

Neither answer is universally correct. The right call depends on who needs to change it, how often, and how much you care about it surviving a code review process.

### A worked example

We ran into exactly this fork recently while adding a small feature: letting Lab Scientists see the diagnosis recorded on the Patient Encounter that generated a given Lab Test.

- **Record-based first pass**: a *Client Script* record, attached to the `Lab Test` DocType, editable straight from the Desk UI — no deploy required, but the JavaScript lives as a string inside a database row, with no syntax highlighting and noisy diffs if you don't export it.
- **Making it portable**: exporting that Client Script as a **fixture** (`fixtures/client_script.json`) turns the DB record into a real file in your app, picked up automatically by `bench migrate` on every site. This is the compromise move — record-based mechanism, file-based delivery.
- **Final choice**: a plain `.js` file (`public/js/lab_test.js`) wired through the existing `doctype_js` hook, matching how the app already handled a sibling case (`patient_encounter.js`). Full lintability, clean diffs, no new fixture category to maintain — at the cost of needing a deploy for every future tweak.

All three options reached the identical end-user outcome. The deciding factor was purely: *does this team want another thing living in fixtures, or does it want to keep everything as reviewable code?* That's an implementation-approach decision, not a "correct vs. incorrect" one.

## 4. A Second Axis: Doctype You Own vs. Doctype You Don't

The file-based path has a hidden precondition that's easy to trip over: **Frappe only auto-loads a `.js` (or `.py`) file that sits next to a DocType's JSON if your app is the one that owns that DocType's module.**

Concretely: if `Lab Test` is defined by the Healthcare app, creating `your_app/doctype/lab_test/lab_test.js` does nothing — Frappe resolves the controller path from wherever the DocType record actually lives, not from wherever you'd like it to live. Extending a foreign DocType always has to go through one of:

- a `hooks.py` entry (`doctype_js`, `doc_events`, etc.) pointing at a file in *your* app, or
- a database record (Client Script, Server Script, Custom Field, Property Setter) that attaches to the DocType by name, regardless of who owns it.

This matters because it silently narrows your options. For a DocType you own outright, "just edit the doctype's own files" is on the table. For a DocType owned by core Frappe, Healthcare, HR, or any other installed app, it isn't — you're always working through an attachment mechanism, never a direct edit.

```text
Do you own this DocType's module?
        │
   ┌────┴────┐
  YES        NO
   │          │
   ▼          ▼
Direct file   Hook (file-based)
edit is an        or
option        DB record (record-based)
```

## 5. A Bigger-Grain Version: New DocType vs. Extending an Existing One

Zoom out one more level and the same file-vs-record, own-vs-foreign tension reappears at the schema-design stage, before you've written any logic at all.

When a new requirement shows up, you're often choosing between:

- **Modeling it as a brand-new DocType** you control completely — full ownership of fields, permissions, and lifecycle, but more schema to design and maintain.
- **Extending an existing DocType** via Custom Field, Property Setter, or a child table addition — faster, and it keeps the new attribute close to the concept it describes, but you're now dependent on someone else's schema not changing underneath you.

A rough heuristic: if the new thing is genuinely a first-class concept with its own identity, permissions, and workflow (an `Insurance Claim`, say), make it a DocType. If it's really just an attribute or annotation on something that already exists (a diagnosis note visible on a Lab Test), extend the existing DocType instead of inventing a new one to hold a single field.

---

## 6. Business Logic Placement: Explicit Call vs. Implicit Hook vs. DB Script

A third recurring fork, orthogonal to the first two, is about **when and how your logic actually runs**:

- **A whitelisted method** (`@frappe.whitelist()`) that the frontend calls explicitly via `frappe.call()` — the logic runs only when something asks for it, and the call site is visible in the client code.
- **A `doc_events` hook** in `hooks.py` — the logic runs implicitly, triggered by the framework itself on `validate`, `on_submit`, `after_insert`, and so on, with no explicit call site anywhere.
- **A Server Script** — the same implicit-trigger idea as `doc_events`, but the code lives as a database record instead of a file, so it's editable from the UI and exportable via fixtures, same as Client Script.

The tradeoffs mirror what we've already seen: explicit calls are easier to trace and reason about but require the caller to remember to make them; implicit hooks guarantee the logic always runs regardless of entry point (Desk, Portal, API, import) but are easy to lose track of when debugging; DB-stored scripts trade lintability for no-deploy editability.

The getting-encounter-diagnoses example from earlier used the explicit-call approach on purpose: the Lab Test form needed to *ask* for the diagnosis on demand, not have it injected on every save, so a whitelisted method fit naturally. If instead the requirement had been "automatically flag any Lab Test whose encounter diagnosis matches a critical-care list," that's a `validate`/`on_submit` hook instead — the logic needs to fire whether or not anyone remembers to call it.

## 7. A Decision Checklist

Pulling the threads together, here's a reusable set of questions for the next time you're choosing an implementation approach rather than an application environment:

1. **Do you own this DocType's module?**
 If no, direct file edits are off the table — you're choosing between a hook and a DB record either way.

2. **Does this need to be identical across every environment (dev, staging, prod) without manual re-entry?**
 Favor file-based (with a hook), or a DB record exported as a fixture. Anything not captured as a fixture is effectively local to one site.

3. **Does a non-developer need to change this without going through a deploy?**
 Favor a DB record (Client Script, Server Script, Query Report, Custom Field). This is the strongest argument in favor of record-based approaches.

4. **Do you care about code review, lint tooling, and clean diffs for this logic?**
 Favor file-based. Logic embedded as a string inside a JSON fixture is functionally version-controlled but practically much harder to review.

5. **Should this logic run automatically regardless of which client triggers it (Desk, Portal, API, data import)?**
 Use `doc_events` or a Server Script, not a whitelisted method the frontend has to remember to call.

6. **Is this logic security- or permission-relevant?**
 Regardless of which implementation approach you pick, enforce it server-side. This isn't really a fork — it's a constraint that applies no matter which path above you choose. Client-side checks, however they're delivered, are a UX nicety, not a security boundary.

---

## 8. Closing Thought

Article 1's core principle was: *Frappe provides the application and domain platform; the developer chooses how users interact with it.* This article's version of that principle is narrower but just as practical:

> **Frappe usually offers more than one plumbing path to the same technical outcome — the job isn't to find "the" way to do it, but to pick the implementation approach whose tradeoffs match your team's actual constraints.**

Some teams will standardize on file-based approaches everywhere, treating anything editable through the UI as a maintenance risk. Others will lean on DB-record approaches for anything that non-developers need to tweak, accepting the fixture-export overhead as the price of that flexibility. Both are legitimate conventions — and having a name for the choice (implementation approach, not "the right way") is what makes it possible to write that convention down and actually follow it consistently.
