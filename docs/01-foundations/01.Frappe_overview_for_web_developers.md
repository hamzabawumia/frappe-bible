# Frappe Framework: A General Overview for Web Developers

## 1. Introduction

Frappe is a full-stack web application framework built around a powerful metadata-driven architecture. It provides much more than a backend API: it can provide the **data model, business logic, authentication, permissions, database access, forms, lists, reports, web pages, APIs, background jobs, and application UI**.

For a web developer coming from Django, Laravel, Rails, Node.js, Vue, React, or similar frameworks, the most important thing to understand is that **Frappe does not force you to build the frontend and backend separately**.

Instead, Frappe gives you several application entry points, all of which can ultimately work with the same DocTypes, permissions, validation rules, and business logic.

A useful mental model is:

```text
                         FRAPPE FRAMEWORK
                                │
                     ┌─────────────────────┐
                     │       DocTypes      │
                     │                     │
                     │ Data + Domain Logic │
                     │ Validation          │
                     │ Permissions         │
                     │ Workflow            │
                     └──────────┬──────────┘
                                │
               ┌────────────────┼────────────────┐
               │                │                │
               ▲                ▲                ▲
             DESK             PORTAL             API
               │                │                │
        ┌──────┴──────┐   ┌─────┴─────┐   ┌─────┴─────┐
        │             │   │           │   │           │
        ▲             ▲   ▲           ▲   ▲           ▲
     Standard      Custom Guest   Authenticated REST/RPC
     DocType       Pages  Pages      Pages          APIs
       Views
```

This is the core architectural model to keep in mind.

---

# 2. The Most Important Concept: DocTypes

If you are new to Frappe, start by understanding **DocTypes**.

A DocType is roughly comparable to a combination of:

- a database model
- a form definition
- a CRUD controller
- validation rules
- permissions
- metadata
- workflow configuration
- part of the domain/business layer

For example, a hospital application might have:

```text
Patient
Doctor
Appointment
Patient Encounter
Prescription
Lab Order
Sales Invoice
Payment
```

An `Appointment` DocType might contain:

```text
patient
doctor
appointment_date
appointment_time
status
notes
```

Frappe uses the DocType definition to understand how that data should be stored, displayed, validated, accessed, and secured.

This is one of the major differences between Frappe and many traditional web frameworks.

Instead of thinking:

```text
Database Model
      ↓
Controller
      ↓
Form
      ↓
API
      ↓
Frontend
```

you should initially think:

```text
                 DocType
                    │
        ┌───────────┼───────────┐
        │           │           │
      Data       Business    Metadata
                  Logic
        │           │           │
        └───────────┼───────────┘
                    │
             Multiple Interfaces
```

The same DocType can be used through Desk, Portal pages, and APIs.

---

# 3. The Three Frappe Application Environments

Frappe applications can be understood through three primary environments:

1. **Desk**
2. **Portal / Website**
3. **API / Headless**

These are not three completely separate backends.

They are different ways of interacting with the same Frappe application and its DocTypes.

---

# 4. Environment 1: Desk

## What is Desk?

Desk is Frappe's authenticated internal application environment.

It is normally used by:

- administrators
- staff
- doctors
- accountants
- teachers
- managers
- support staff
- other internal users

A typical Desk URL might look like:

```text
/app/patient
/app/patient/PAT-00001
```

The important thing is that Desk is already a complete application environment.

You do not necessarily need to build:

- authentication
- navigation
- forms
- list views
- permissions
- search
- filtering
- CRUD handling

from scratch.

Frappe can provide these automatically from the DocType definition.

---

# 5. Standard Desk CRUD

The simplest Frappe development approach is to create a DocType and allow Frappe to generate the standard interface.

For a DocType such as:

```text
Patient
```

Frappe can provide:

- Form View
- List View
- Search
- Filters
- Sorting
- Create
- Read
- Update
- Delete
- Permissions
- Attachments
- Comments
- Version history
- Workflow support where configured

Depending on the DocType and configuration, other views such as:

- Kanban
- Calendar
- Gantt
- Reports

can also be available.

This means that a developer can build a functional CRUD application with surprisingly little frontend code.

For example:

```text
Create Patient DocType
        │
        ▼
Frappe generates
        │
        ├── Patient Form
        ├── Patient List
        ├── Search
        ├── Filters
        ├── Permissions
        └── CRUD operations
```

This is the **standard Frappe CRUD experience**.

---

# 6. Custom Desk Pages

Standard DocType forms are not the only option.

You can create a **Custom Desk Page** when the standard form/list interface is not appropriate.

Examples:

```text
/app/patient-browser
/app/course-browser
/app/doctor-dashboard
/app/lab-dashboard
/app/student-dashboard
```

A custom Desk page can contain your own interface.

For example:

```text
Frappe Desk
     │
     ▼
Custom Desk Page
     │
     ▼
HTML / CSS / JavaScript
     │
     ▼
Frappe API
     │
     ▼
DocTypes
```

You can use technologies such as:

- plain JavaScript
- Frappe JavaScript APIs
- HTML/CSS
- HTMX
- Alpine.js
- Vue
- React
- other frontend libraries

For example:

```text
Frappe Desk
     │
     ▼
Custom Desk Page
     │
     ▼
HTMX
     │
     ▼
Frappe Python API
     │
     ▼
DocType
```

This is particularly useful when building interfaces that do not look like traditional Frappe forms.

For example, an LMS might prefer:

```text
┌───────────────────────────────┐
│ Course                        │
│                               │
│ Introduction to Python        │
│ ███████████████░░░░ 75%       │
│                               │
│ [ Continue Learning ]         │
└───────────────────────────────┘
```

rather than a traditional DocType form.

The application can still remain entirely inside Frappe Desk.

---

# 7. Environment 2: Portal / Website

The second major environment is Frappe's website/portal layer.

This is where you build experiences for users who interact with your application through the website rather than the internal Desk interface.

There are two important situations:

1. Public / Guest pages
2. Authenticated Portal pages

---

# 8. Public / Guest Pages

A public page is accessible without logging into Frappe.

Examples include:

```text
/courses
/register
/contact
/apply
/book-appointment
```

These pages can be used for:

- public registration
- lead capture
- applications
- public directories
- public booking
- marketing pages
- information pages

You can build these using technologies such as:

- Jinja
- HTML
- CSS
- JavaScript
- HTMX
- Web Forms
- whitelisted Python methods

For example:

```text
Guest Browser
      │
      ▼
Frappe Website Page
      │
      ▼
Jinja / HTML / JS / HTMX
      │
      ▼
Frappe Backend
      │
      ▼
DocType
```

---

# 9. Authenticated Portal Pages

A portal page is different because the user has logged into Frappe.

Examples include:

```text
/student
/student/courses
/student/profile

/patient
/patient/appointments

/customer
/customer/orders
```

These pages can provide a completely different experience from Desk.

For example:

```text
Student Portal

┌───────────────────────────────────┐
│ Welcome, Ama                      │
├───────────────────────────────────┤
│                                   │
│ My Courses                        │
│                                   │
│ Twi Beginner                      │
│ ███████████░░░ 65%                │
│                                   │
│ Python for Kids                   │
│ ███████░░░░░░░ 40%                │
│                                   │
└───────────────────────────────────┘
```

The user is still authenticated by Frappe.

The application can still use Frappe's:

- users
- roles
- permissions
- DocTypes
- APIs
- business logic

The developer simply chooses to present a different interface.

---

# 10. Web Forms

Web Forms are another important part of the website/portal environment.

They are useful when a user needs to submit data through a web interface that corresponds closely to a DocType.

For example:

```text
Public Registration Form
          │
          ▼
       Web Form
          │
          ▼
       DocType
```

This can be useful for:

- registration
- applications
- lead capture
- simple submissions
- booking requests
- public data collection

Web Forms are therefore one of the ways Frappe can provide CRUD-like interactions outside Desk.

---

# 11. Environment 3: API / Headless Frappe

The third environment is the API layer.

Here, Frappe acts primarily as the backend.

The frontend may be completely separate.

For example:

```text
React
   │
   │ HTTP
   ▼
Frappe API
   │
   ▼
DocTypes
```

Or:

```text
Vue
   │
   ▼
Frappe REST API
   │
   ▼
DocTypes
```

Or:

```text
Mobile App
   │
   ▼
Frappe API
   │
   ▼
DocTypes
```

Or:

```text
HTMX
   │
   ▼
Frappe API
   │
   ▼
DocTypes
```

Frappe therefore does not require the frontend to be built with Frappe's own UI.

---

# 12. Frappe REST API

Frappe provides a REST API for working with DocTypes.

Conceptually:

```text
/api/resource/Patient
```

can expose the Patient resource.

This allows external applications to communicate with Frappe using HTTP.

For example:

```text
Frontend
    │
    │ HTTP
    ▼
Frappe REST API
    │
    ▼
Patient DocType
    │
    ▼
Database
```

This makes Frappe suitable as a backend platform for:

- SPAs
- mobile applications
- external websites
- integrations
- other services

---

# 13. Whitelisted Python Methods

Frappe also allows developers to expose Python functions as API endpoints using:

```python
@frappe.whitelist()
def get_patients():
    ...
```

The frontend can then call that backend method.

For example:

```text
Custom Frontend
       │
       ▼
frappe.call()
       │
       ▼
Whitelisted Python Method
       │
       ▼
Frappe DocTypes
```

This is useful when the application requires business operations that are more complex than simple CRUD.

For example:

```python
@frappe.whitelist()
def book_appointment(patient, doctor, date):
    ...
```

The method could:

1. validate the patient
2. check the doctor's availability
3. check permissions
4. create an Appointment
5. trigger notifications
6. return the result

The frontend does not need to know how those business rules work.

---

# 14. Custom APIs

You can also create custom API structures when the built-in REST resources or whitelisted methods are not sufficient.

This is useful when you want an API designed specifically for another application.

For example:

```text
GET /api/myapp/student/dashboard
```

could return:

```json
{
    "student": {...},
    "courses": [...],
    "progress": [...],
    "assignments": [...]
}
```

The important architectural point is that Frappe can act as a complete backend/API platform rather than merely as a source of database CRUD endpoints.

---

# 15. Frontend Technologies Are Not Architectural Environments

This is one of the most important concepts for a developer new to Frappe.

Technologies such as:

- HTMX
- Alpine.js
- Vue
- React
- Angular
- Svelte
- plain JavaScript

are **frontend technologies**.

They are not separate Frappe CRUD architectures.

For example, all of these are possible:

```text
Custom Desk Page
      │
      ▼
HTMX
      │
      ▼
Frappe API
```

```text
Custom Desk Page
      │
      ▼
Vue
      │
      ▼
Frappe API
```

```text
Custom Desk Page
      │
      ▼
React
      │
      ▼
Frappe API
```

Likewise, on the portal:

```text
Portal Page
     │
     ▼
HTMX
     │
     ▼
Frappe Backend
```

```text
Portal Page
     │
     ▼
Vue
     │
     ▼
Frappe API
```

```text
Portal Page
     │
     ▼
React
     │
     ▼
Frappe API
```

Therefore:

> **HTMX, Vue, React, Alpine.js, and plain JavaScript are implementation choices at the presentation layer.**

They do not define the underlying Frappe architecture.

When designing a Frappe application, ask three separate questions.

## Question 1: Where does the application live?

```text
Desk
Portal / Website
API / Headless
```

## Question 2: How is the user interface implemented?

```text
Frappe Native UI
HTML + JavaScript
HTMX

```

## Question 3: How does the UI reach the domain layer?

```text

Whitelisted Python methods

```

This gives a much clearer architectural picture.

# 18. The Domain Layer Is the Common Foundation

A critical architectural principle is that the business rules should not depend on whether the user is accessing the system through Desk, Portal, or an external application.

For example, suppose a hospital has a rule:

> A doctor cannot book two appointments for the same time slot.

That rule should belong to the backend/domain layer.

It should not exist only in:

```text
React
```

or only in:

```text
Desk JavaScript
```

or only in:

```text
HTMX
```

Instead:

```text
Desk
   │
   ├──────────────┐
   │              │
Portal            │
   │              │
API               │
   │              │
   └───────┬──────┘
           ▼
     Business Rules
           │
           ▼
      Appointment
```

This allows multiple interfaces to safely use the same application.

# 20. Frappe Is Not Just an Admin Panel

A common misunderstanding among developers coming from other frameworks is:

> "Frappe is mainly an admin panel for database CRUD."

That is too narrow.

Frappe can be used to build:

- internal business applications
- ERP systems
- hospital systems
- LMS platforms
- CRM applications
- portals
- public websites
- APIs
- mobile backends
- integrations
- workflow-driven systems

The standard Desk UI is simply one of the ways users can interact with the application.

# 21. Frappe and Traditional Web Frameworks

A simplified comparison can help.

A traditional framework might encourage:

```text
Models
   │
Controllers
   │
Templates / API
   │
Frontend
```

Frappe provides many of these capabilities through its metadata and DocType system:

```text
DocType
   │
   ├── Database representation
   ├── Form metadata
   ├── Permissions
   ├── Validation
   ├── Workflow
   ├── API access
   └── UI generation
```

You can still write custom Python, JavaScript, HTML, CSS, and API code.

Frappe simply provides a much larger application foundation.

# 22. Frappe Apps

Frappe applications are packaged as **apps**.

An app contains the code and metadata for a particular application or domain.

For example:

```text
my_hospital_app
my_lms_app
my_clinic_app
my_school_app
```

An app can contain:

```text
DocTypes
Python code
JavaScript
Web pages
Portal pages
Desk pages
Reports
Print formats
Workflows
Hooks
API methods
Background jobs
Fixtures
```

A Frappe site can have multiple apps installed on it.

This allows the framework to be extended without modifying Frappe's core code.

---

# 23. Frappe's Metadata-Driven Approach

One of Frappe's defining characteristics is that much of the application is represented as metadata.

For example, a DocType can describe:

```text
Name
Fields
Field Types
Required fields
Permissions
Naming
Workflow
Child tables
Links
UI behavior
```

Frappe uses this information to provide application functionality.

This is why creating a DocType can immediately result in a usable CRUD interface.

It is also why Frappe applications can be developed rapidly.

---

# 24. Child Tables

Frappe DocTypes can contain child tables.

For example:

```text
Sales Invoice
│
├── Customer
├── Posting Date
└── Items
     │
     ├── Item
     ├── Quantity
     ├── Rate
     └── Amount
```

The child table is itself represented by a child DocType.

This is useful for structures such as:

```text
Patient Encounter
   ├── Prescriptions
   ├── Lab Tests
   └── Procedures
```

or:

```text
Course
   └── Lessons
```

or:

```text
Order
   └── Order Items
```

Understanding child tables is essential for Frappe development.

---

# 25. Permissions

Permissions are another major part of Frappe's architecture.

Frappe provides role-based access control.

For example:

```text
Administrator
Doctor
Nurse
Teacher
Student
Accountant
```

can have different permissions for different DocTypes.

The developer should therefore avoid treating frontend hiding as security.

For example, hiding:

```text
[Delete]
```

with JavaScript does not constitute security.

The backend must enforce the permission.

A good mental model is:

```text
Frontend visibility
       ≠
Security

Backend permission
       =
Security
```

---

# 26. Server-Side Validation

Business rules should also be enforced on the server.

For example:

```text
Appointment
    │
    ▼
Validate
    │
    ├── Patient exists
    ├── Doctor exists
    ├── Time is valid
    ├── Doctor is available
    └── User is permitted
```

Client-side JavaScript can improve user experience, but it should not be the only place where important business rules exist.

This becomes especially important when the same DocType is accessed through:

- Desk
- Portal
- REST
- mobile applications
- integrations

All of those clients must obey the same backend rules.

---

# 27. `frappe.call()`

`frappe.call()` is one of the common ways frontend JavaScript communicates with Python methods in Frappe.

Conceptually:

```text
JavaScript
    │
    ▼
frappe.call()
    │
    ▼
Python method
    │
    ▼
DocType / Database
```

For example, a frontend might call a method that returns available appointment slots.

The important principle is:

> The browser should request an operation; the server should own the business logic.

---

# 28. HTMX in Frappe

HTMX fits naturally into this architecture.

HTMX is not a Frappe subsystem.

It is a frontend technology that can be used to make HTTP requests and update parts of an HTML interface.

For example:

```text
Custom Desk Page
      │
      ▼
HTMX
      │
      ▼
Frappe endpoint
      │
      ▼
Jinja / HTML response
```

This can be an attractive architecture when you want rich interactive pages without building a full SPA.

For example:

```text
Course Browser
      │
      ├── Search
      ├── Filter
      ├── Pagination
      ├── Course cards
      └── Enrollment
```

can be built using HTML, Jinja, HTMX, and Frappe's backend.

---

# 29. Vue and React in Frappe

Vue and React are equally possible.

For example:

```text
Frappe Desk
     │
     ▼
Custom Desk Page
     │
     ▼
React Application
     │
     ▼
Frappe API
```

or:

```text
Frappe Portal
     │
     ▼
Vue Application
     │
     ▼
Frappe API
```

The important point is that Frappe does not require developers to use one particular frontend framework.

The choice depends on the application's needs.

A developer might choose:

```text
Native Frappe UI
```

when standard CRUD is enough.

Choose:

```text
HTMX
```

when server-rendered HTML and lightweight interactivity are desirable.

Choose:

```text
Vue / React
```

when the application requires a more complex client-side application.

# 31. Common Beginner Mistakes

## Mistake 1: Thinking Frappe means Desk

Desk is only one application environment.

```text
Frappe
 ├── Desk
 ├── Portal
 └── API
```

---

## Mistake 2: Thinking HTMX is an alternative to Frappe

It is not.

HTMX is a frontend technology.

```text
Frappe
   +
HTMX
```

is perfectly normal.

---

## Mistake 3: Thinking React means abandoning Frappe

It does not.

You can use:

```text
React
   +
Frappe API
   +
Frappe DocTypes
```

---

## Mistake 4: Putting business rules only in JavaScript

This creates problems when another client accesses the same backend.

Business rules should primarily be enforced server-side.

---

## Mistake 5: Treating the database as the domain layer

Developers coming from traditional CRUD applications may be tempted to write SQL everywhere.

Frappe encourages you to work through its document and application layer where appropriate.

The DocType is more than a database table.

---

# 32. Recommended Development Mindset

When starting a new Frappe feature, ask:

### Step 1 — What is the domain object?

For example:

```text
Patient
Appointment
Course
Lesson
Student
Invoice
```

Create the appropriate DocType.

### Step 2 — What are the business rules?

For example:

```text
A doctor cannot have overlapping appointments.
A student cannot enroll twice.
An invoice cannot be edited after submission.
```

Implement important rules on the server.

### Step 3 — Who uses the feature?

```text
Staff
Student
Patient
Customer
Public user
External application
```

### Step 4 — Which environment should they use?

```text
Desk
Portal
API
```

### Step 5 — What frontend technology is appropriate?

```text
Native Frappe UI
HTML/Jinja
HTMX
Alpine.js
Vue
React
etc.
```

This prevents the common mistake of choosing a frontend technology before understanding the application architecture.

---

# 33. A Practical Decision Matrix

| Requirement | Recommended starting point |
|---|---|
| Simple internal CRUD | Standard DocType + Desk |
| Complex internal dashboard | Custom Desk Page |
| Public form | Web Form |
| Public website page | Portal / Website |
| Customer/student/patient area | Authenticated Portal |
| Lightweight interactive UI | HTMX |
| Small client-side interactions | Alpine.js |
| Complex SPA | Vue or React |
| Mobile application backend | Frappe API |
| External system integration | REST / custom API |
| Complex business operation | Whitelisted/custom Python method |
| Highly customized internal application | Custom Desk Page + chosen frontend |

These are starting points, not strict rules.

```text
    Standard    Custom  Public   Authenticated REST/RPC
      CRUD      Pages   Pages       Pages       APIs
       │           │       │           │           │
       └───────────┴───────┴───────────┴───────────┘
                               │
                               ▼
                      FRONTEND TECHNOLOGIES
                               │
              ┌────────────────┼────────────────┐
              │                │                │
             HTMX             Vue             React
              │                │                │
           Alpine          JavaScript       Svelte/etc.
```

The three architectural questions are therefore:

```text
1. WHERE does the application live?
   Desk / Portal / API

2. HOW is the interface implemented?
   Native UI / HTML / HTMX / Vue / React / etc.

3. HOW does it reach the domain layer?
   DocType APIs / frappe.call() / REST / custom APIs
```

# 35. The Core Principle

The most useful sentence to remember is:

> **Frappe provides the application and domain platform; the developer chooses how users interact with it.**

Frappe can provide:

```text
Data
Business Logic
Permissions
Authentication
Validation
Workflow
CRUD
APIs
Background Processing
UI Infrastructure
```

while the developer can choose:

```text
Desk
Portal
API

and

Native Frappe UI
HTML/Jinja
HTMX
Alpine.js
Vue
React
Svelte
Mobile clients
```

This is why Frappe should not be thought of simply as an "admin panel framework."

It is better understood as a **full-stack application platform with multiple presentation and integration entry points, centered around DocTypes and server-side business logic**.
